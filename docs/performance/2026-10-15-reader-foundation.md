# 阅读器基础（0.4 开发分支）性能测试报告

**日期**：2026-10-15
**对比对象**：0.3.0（`29925c3`）与 `feat/reader-foundation`（`03c1bc6`，即预览按需消毒之后的代码；此后的提交只改样式、生成的类型和文档）
**原始数据**：[raw/2026-10-15/](raw/2026-10-15/)（`environment.txt`、各套件逐轮输出、`summary.md`）
**复现**：`ROUNDS=2 scripts/bench/run.sh 29925c3 docs/performance/raw/<日期>`，约 8 分钟

## 结论

- **写作**：每输入一个字的开销，10 万字文稿从约 25 ms 降到约 2.6 ms，30 万字从约 60 ms 降到约 8.7 ms，都在一帧（16 ms）以内。移动光标在 30 万字文稿中从约 46 ms 降到约 4 ms。
- **后台**：空闲时每 2 秒一次的轮询，在 300 份草稿下从约 65 ms 降到约 2 µs。打开最近文稿从约 63 ms 降到约 0.04 ms。2 MB 文稿中移动光标或滚动后保存位置从约 24 ms 降到约 3 ms。
- **没有退化**：保存、启动、纯 Markdown 的预览与 0.3.0 持平，差异在噪声范围内。
- **有代价的一项**：文稿只要含原始 HTML（例如 README 开头居中的标志），预览就要整篇过 DOMPurify，耗时约为 0.3.0 的 4 倍：2 万字约 18 ms，10 万字约 96 ms。0.3.0 不渲染原始 HTML，只把标签当文字原样显示，所以不需要消毒。本分支开始渲染 README 里常见的 HTML，为此必须消毒，这是新能力的代价。不含 HTML 的文稿已在 `03c1bc6` 中跳过消毒。

## 后续复查（2026-10-16）

- 英文界面提交 `4876052` 让编辑器的每个图片、表格、任务框小部件在创建时都判断一次界面语言，而每次按键和移动光标都会重建全篇的块级小部件。桌面应用里这只是读取 `window.mygo.locale`；本报告的编辑器基准运行在 Bun 中，那里每次判断都要抛出并捕获异常。同机交替单独计时 30 万字文稿的块级装饰：英文界面之前约 4.2 ms，之后约 7.5 ms；`9037969` 改为读取缓存的语言后约 4.5 ms。
- 同一次复查发现：机器繁忙时，一次编辑可能用完 CodeMirror 每次 20 ms 的解析预算，只留下不完整的语法树；之后的编辑只处理已解析的部分，会显得过快。`scripts/bench/editor.ts` 和 `scripts/check-performance.ts` 现在会发现这样的批次，补完语法树后重测。修正后的编辑器基准在 `7f0acf4` 的代码上跑了一轮：10 万字输入一个字，0.3.0 为 23.8 ms、本分支 3.9 ms；30 万字为 79.2 ms、10.2 ms；30 万字移动光标为 78.7 ms、6.7 ms。与上文表格的范围相符或略高；只跑了一轮，当时负载较高，原始数据未更新。

## 方法

- **同条件对比**：用 `git archive` 取出 0.3.0 源码，与当前工作区共用同一份 `node_modules`。CodeMirror、markdown-it 等库的版本完全相同，差异只来自应用代码。
- **交替执行**：每轮依次跑编辑、预览、存储三组，每组先 0.3.0 后本分支，共 2 轮。负载变化会同时落在两边。
- **编辑**（`scripts/bench/editor.ts`）：
  - 文稿是 2 万、10 万、30 万字的中文，带加粗、链接、代码、列表、待办、表格和图片。
  - 「输入一个字」在文稿中部插入一个字；「移动光标」在中部来回移动 40 个字符。
  - 计时包括 CodeMirror 状态更新、增量解析和即时排版装饰的重建。0.3.0 每次都整篇重建装饰。本分支只重建块级部件和可见区的行内装饰；可见区按中部 6000 字模拟，相当于一屏多。
  - 每批 20 次操作，取 5 批中的最好值。
  - 「仅解析」是不带任何装饰的同样输入，只作下限参考。
- **字数**：0.3.0 每次按键都整篇统计（去掉空白后数字符）。本分支停止输入 400 ms 后统计一次，并且不计 Markdown 符号。
- **预览**（`scripts/bench/preview.py`）：在 Chrome 中调用各自的 `renderMarkdown` 并插入页面。文稿有三种：
  - 纯 Markdown；
  - README 式，只在开头有一个居中标志的 HTML 块；
  - 每节都有 HTML 块。

  每批 10 次渲染，取 5 批中的最好值。
- **存储**（`perf_bench_test.go`，构建标签 `perf`）：数据目录放 300 份约 30 KB 的草稿，外加一个 2 MB 的本地文件文稿。0.3.0 用 `scripts/bench/legacy_perf_test.go.txt` 跑同样的场景，只用 0.3.0 已有的接口：空闲轮询是 `State()`，保存光标位置是一次内容不变的 `Update`。参数为 `-benchtime 20x -count 3`。

## 解读

### 写作

0.3.0 的即时排版每次按键、每次移动光标都整篇重建装饰。文稿越长，每个字越慢：10 万字约 25 ms，已经超过一帧；30 万字约 60–90 ms，打字会明显跟不上。

本分支把装饰拆成两部分：
- 表格、图片等块级部件放在状态字段里，只遍历顶层块节点；
- 加粗、链接、标题标记等行内装饰只算可见区。

现在每个字的开销主要是增量解析和块级遍历，30 万字也在一帧以内。移动光标不改文档，不需要重新解析，30 万字时约 4 ms。

这里测的是 JavaScriptCore 中状态与装饰的计算，不含 WebKit 的 DOM 更新和绘制。两个版本都只绘制可见区，这部分开销相近。

### 后台与存储

- **空闲轮询**：0.3.0 窗口每 2 秒调用一次 `State()`。每次都要完整读取并哈希当前文件，对全部草稿的全文重新截取摘要，再把含正文的整个状态传回页面。300 份草稿加一个 2 MB 文件时，仅 Go 端就约 65 ms，不含传回页面的序列化。这等于空闲时也持续占用约 3% 的一个核。本分支改为 `Status(id)`：文件大小、修改时间和 inode 不变时只做一次 `stat`，只回传版本号和状态。窗口不可见时也不再轮询。
- **最近文稿**：每份草稿的摘要只在内容变化时生成一次并保存，不再每次对全部草稿的全文分词截取。
- **光标与滚动位置**：0.3.0 每次都带 fsync 重写整篇草稿 JSON，2 MB 文稿约 24 ms。本分支只写 `positions.json`，也不 fsync；断电时最多丢失最近一次光标位置，正文不受影响。
- **保存与启动**：两边的范围重叠，没有退化。本地文件写回由 3 次原子写减为 2 次（0.3.0 会把草稿 JSON 写两次），同时新增了保留 Finder 标签、扩展属性和创建时间的步骤。启动时多了坏文件隔离和空草稿清理，没有可测的额外开销。

### 预览

- **纯 Markdown**：markdown-it 会转义正文中的一切，不需要消毒。`03c1bc6` 起这类文稿跳过 DOMPurify，与 0.3.0 持平。还剩约 10% 的差距，来自新增的裸链接识别、脚注、提示块和语义类名插件，以及先解析到惰性 `<template>` 再插入页面。
- **含原始 HTML**：0.3.0 关闭了 markdown-it 的 HTML 支持，`<p align="center">` 之类的标签会作为文字显示，表中 0.3.0 的数字是这种输出的耗时。本分支渲染这些 HTML：只要有一处作者写的 HTML，整篇都过 DOMPurify。耗时取决于文稿长度，与 HTML 的多少无关：「开头一个 HTML 块」和「每节都有」几乎一样。10 万字时单独计时如下：

  | 步骤 | 耗时 |
  |---|---:|
  | markdown-it 解析与生成 HTML | 约 6.8 ms |
  | 解析到 `<template>` | 约 6.2 ms |
  | DOMPurify | 约 43 ms |

  试过两种改法，都没有可测收益，主要开销是 DOMPurify 逐个节点的检查：
  - 原地消毒（`IN_PLACE`），省掉一次序列化和再解析；
  - `setConfig` 预先设好配置。
- **对用户的影响**：阅读模式在打开和内容变化时渲染一次。分栏预览在停止输入 250 ms 后渲染一次。常见的 2 万字以内的 README 约 18 ms，感觉不到。10 万字以上又含 HTML 的文稿，停顿后会有约 0.1 秒的卡顿。

### 字数

本分支的统计会排除 Markdown 符号，单次比 0.3.0 慢约 3 倍。但它只在停止输入 400 ms 后运行一次：连续打字时开销为 0，停顿时 10 万字约 3 ms。0.3.0 每个字都要付 1 ms（10 万字）到 10 ms（100 万字）。

## 局限

- 机器负载高，绝对值偏保守。保存、启动这类范围重叠的场景只能说明没有退化，不能给出精确倍数。
- 编辑器基准是 JavaScriptCore，但没有 DOM。预览基准是 Chrome（V8 + Blink），不是 WKWebView。两者适合前后对比，不代表应用内的绝对耗时。
- 没有测：应用冷启动时间、内存占用、PDF 导出耗时、WKWebView 中从按键到上屏的端到端延迟。

## 后续可做

- 预览按块增量渲染：只重渲染改动的顶层块。这对所有文稿都有效，也能把含 HTML 文稿的消毒限制在改动的块。
- 只对作者 HTML 所在的子树消毒，Markdown 生成的部分不再逐节点检查。这需要自己遍历 DOM，属于安全敏感改动，应单独评审。
- 超长文稿按上次渲染耗时自动放宽分栏预览的停顿时间。
