# 升级 MyGo 0.7.1：验证记录

对应[实施计划](../plans/2026-10-27-mygo-0.7.md)，随 0.6.6 发布。

## 开发

- **traecli**：
  - Task 1：MyGo 和 mygo-runtime 升到 0.7.1，Go 升到 1.27.3。`go tool mygo generate` 重新生成的文件与原来相同，`web/app.js` 不变。发版文档改用新的安装包名。
  - Task 3：macOS 顶栏左侧的留白改用 MyGo 的 `--mygo-titlebar-inset-left`。
- **Codex**：Task 2，在另一个 worktree 里完成：
  - 删掉 `allowForegroundHandoff`，这件事 MyGo 0.6.1 起自己做（egoist/mygo#592）；
  - 版本号改由 `App.Version()` 从包信息读取，发版只改 `mygo.json` 和 `package.json`；
  - 补了真实文件系统的原子保存测试。
- **Claude**：
  - 逐行审查，替 Codex 提交（它的沙箱写不了共享的 git 索引），挑到升级分支上合并，统一复跑。
  - 计划文档里原有一条检查命令，带着会让人联想到内部 npm 镜像的字样；推送后改成了中性写法，并重写了这个分支。

## 自动检查

在合并后的分支上运行，与 `9933de6` 相同。

- **静态检查**：`go vet ./...`、`GOOS=windows go vet ./...`、`go test ./...`、`go tool mygo i18n check`（496 条消息）、`check-i18n`、`tsc --noEmit`、`check-editor` 全部通过。
- **单元检查**：17 项 bun 单元检查全部通过。
- **性能**：`check-performance` 按默认预算通过。
- **构建**：`node scripts/build.mjs` 重建的 `web/` 与提交的一致。
- **浏览器回归**：Chrome 回归 17 项。
  - 第一遍时 15 分钟平均负载高达 37，`check-tables`、`check-images`、`check-english` 失败，每次挂在不同的行。`check-mermaid` 只有那条已知的 CSP 断言失败。
  - `check-english` 重跑通过。
  - `check-tables` 和 `check-images` 在负载 8–22 时与 `main` 交替各跑两轮：分支 4/4 通过，`main` 的 `check-images` 有一次失败。所以判断为负载引起的偶发失败，不是回归。
  - 两边的 `-web` 服务端接口耗时相同：每次 `State` 调用的中位数是 0.4 和 0.5 ms，空闲时 CPU 都是 0。
- **CI**：Windows（`go vet`、`go test`，含新的原子保存测试）和 Performance 在 `9933de6` 和发版提交 `72d986a` 上都通过。

## 兼容性

- **更新**：MyGo 0.6.0 到 0.7.1 之间，`internal/update` 只改了 `github.go`（预发布版的更新源），清单和增量包的格式没有变。已安装的 0.6.5（MyGo 0.6.0 的更新器）可以读取新清单，并使用 0.7.1 做的增量包。
- **安装包改名（MyGo 0.7.0）**：
  - 改为 `liubai-<版本>.dmg` 和 `liubai-setup-<版本>-<架构>.exe`；更新包和更新清单的名字不变。
  - 官网原来按 `.amd64.exe`、`.arm64.exe` 认 Windows 安装包，echovic-apps `af429cd` 改为 `amd64.exe`、`arm64.exe`，新旧文件名都能匹配。

## 没有做的

- **桌面应用实测**：没有在原生应用里试。全屏时顶栏留白的变化依据的是 MyGo 文档（全屏时 inset 为 `0px`），浏览器检查用模拟的变量验证了两种值。
- **Windows 真机**：没有，只有 CI。
- **安装脚本**：`install.sh` 和 `install.ps1` 随发布上传了，但没有实测，发布说明里也没有推荐。按规定，这台 Mac 上不安装发布版。
